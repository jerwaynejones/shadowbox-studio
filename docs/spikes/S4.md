# Spike S4: Raw PNG decode and header inspection (`SBPng`)

**Status:** complete, **PASS**. Recommend promoting `spikes/S4/png.js` to `js/png.js`, with the five plan deltas in §6.
**Date:** 2026-10-07. **Plan:** `docs/plans/opaque-layers-dev-plan.md` §6, Task S4. **Requirements:** IMG-01, IMG-02, IMG-05, IMG-07, NFR-05, AT-02, AT-22.
**Integrated:** 2026-10-07 as `js/png.js` with all five §6 amendments; §6.3 resolved as the recommendation (accept by scaling, `ARCHITECTURE.md` D5). CRC-32 moved into `js/util.js`; checks in `test/run_tests.js` suites "spike S4 — …"; plan deltas in Appendix C.
**Third-party code:** none. Inflate uses the platform `DecompressionStream`, SHA-256 uses the existing `SBHash`, and CRC-32 is the existing `zip.js` table algorithm. Nothing was vendored and npm was not used (Appendix B).

Scope note: other spikes were running at the same time, so the spike changed no shared source. The planned move of CRC-32 into `js/util.js` is emulated by `spikes/S4/util_crc32.js`, a shim that adds `SBUtil.crc32` to the real `util.js`. Over 200 random slices it produced the same values as `SBZip.crc32` (200 of 200 equal). The `zip.js` edit and the module registration are left for the real S4 commit.

### Interface as implemented

- `SBPng.inspect(bytes, {verifyCrc = true}) → {w, h, bitDepth, colorType, interlace, animated, exif, paletteGray, hasTRNS, idatBytes, idatCount, chunks}`.
  - It never inflates. It throws a coded error on structural faults (signature, truncation, CRC, IHDR).
  - Internal handles (`_b`, `_idat`, `_plte`, `_trns`) are non-enumerable, so the output stays JSON-clean.
- `SBPng.check(info, mode, {lowBitDepth}) → code | null`.
  - Both modes reject `PNG_APNG` and `PNG_16BIT`.
  - Height mode also rejects `PNG_PALETTE` (a non-gray PLTE) and `PNG_BITDEPTH` (gray at 1, 2 or 4 bits, unless `lowBitDepth: "scale"` is set).
- `await SBPng.decode(bytes, {mode, verifyCrc, lowBitDepth, maxPixels}) → {w, h, samples, alpha, channels, policy, exif, sampleHash, warnings}`.
  - `policy` is one of `raw-gray8`, `raw-rgb-equal`, `raw-palette-gray8`, `raw-grayN-scaled8`, or `raw-rgb` (tonal mode only, `channels: 3`).
  - It implements Step 3 items 1 to 10, including Adam7 at sub-byte depths and tRNS for colour types 0, 2 and 3.

## 4. Findings (measured)

### 4.1 The raw decoder is required: Chromium's default canvas decode rewrites height samples
A 256-step gray ramp with `gAMA = 1.0` came back from `createImageBitmap` → canvas with **254 of 256 samples changed, a maximum difference of 73** (128 became 188). With `gAMA = 0.25`, 254 of 256 changed with a maximum of 58. `SBPng` returns the exact ramp in Node and Chromium. `colorSpaceConversion: "none"` restored the raw values in Chromium, but that is one engine's behaviour and the plan already distrusts browser decode options (coverage #8). An sRGB `iCCP` profile from ImageMagick changed nothing. This confirms IMG-02 and R3: height mode must not use the canvas.

### 4.2 The tonal path still needs `inspect` + `check` with CRC on: Chromium accepts things IMG-01 rejects
| Input | `createImageBitmap` | `SBPng` |
|---|---|---|
| Valid 2-frame APNG | **decoded** (first frame) | `PNG_APNG` |
| 16-bit gray | **decoded** (silently truncated to 8 bits) | `PNG_16BIT` |
| Ancillary `tEXt` CRC corrupt | **decoded** | `PNG_CRC` |
| IDAT CRC corrupt / truncated / no IEND | rejected | `PNG_CRC` / `PNG_TRUNCATED` |

G2.14 already runs `inspect` and `check` in both modes. This spike shows that those calls are the **only** thing standing between the tonal path and an IMG-01 violation. So `inspect` must keep `verifyCrc: true` on intake. It costs about 7 ms/MiB, or 173 ms on the 25 MiB worst case here. Note that the shared fixture `pngEncode({apng: true})` writes `acTL` without `fcTL`, which Chromium rejects as corrupt. A test against that fixture alone would hide the tonal-path gap. G4.8 should use a valid APNG (`gen_corpus.sh` makes one).

### 4.3 Real tools emit sub-8-bit gray; the plan's "reject bit depth ≠ 8" will bite users
ImageMagick's default PNG writer stored a 4-level gray heightmap as **2-bit gray** (`default_4level.png`). A posterized or terraced heightmap is a normal input. The prototype rejects it in height mode by default with the proposed code `PNG_BITDEPTH`, because the plan's code list has no entry for it. It also implements an opt-in `lowBitDepth: "scale"` that maps exactly by the integer factor 255/(2^d − 1), giving ×255, ×85 and ×17. This output **matches libpng/ImageMagick byte-for-byte** (0 differing pixels), and it is not a precision reduction. Gray palettes at 1, 2, 4 or 8 bits are accepted (`raw-palette-gray8`), because their entries are 8-bit by definition.

### 4.4 Fuzzing found a process abort: decode must not trust IHDR for allocation
A random IHDR claiming 2^31−1 × 2^31−1 made `new Uint8Array(expected)` **abort the whole V8 process** (`Check failed: change_in_bytes < kMaxReasonableBytes`, SIGTRAP). It did not throw a catchable `RangeError`. The fix is that `decode` rejects `w*h > maxPixels` (default 2^26, about 67 MP, 4× the desktop envelope) with the proposed `PNG_TOO_LARGE` before it allocates anything. A regression check was added. After the fix, 20,000 mutations produced 0 uncoded errors. Outcomes: 14,692 `PNG_CRC`, 12,314 `PNG_TRUNCATED`, 8,932 `PNG_INFLATE`, 2,809 `PNG_HEADER`, 1,054 `PNG_TOO_LARGE`, and 199 decoded. The IMG-07 preflight is the product limit; this ceiling is the safety floor under it.

### 4.5 `sampleHash` over samples alone collides across dimensions
A 5×1 and a 1×5 image with the same bytes have the same `sampleHash` (pinned by a FINDING check). This is harmless if the hash is always stored next to `w` and `h`. If it is ever used alone as a cache or dedup key (G2.0, `.sbrproj`), it should cover `w, h, policy` plus the samples. One useful property: gray, RGB-equal, RGBA-equal and Adam7 encodings of the same image do share one hash, so the hash identifies content, not encoding.

### 4.6 Error-code boundary differs from the plan list
The plan's seven codes do not cover four reachable failure classes. The prototype adds:

- `PNG_HEADER`: bad or missing IHDR, an illegal depth and colour-type pair, IDAT that is not consecutive, an unknown filter type, a palette index out of range.
- `PNG_INFLATE`: the platform rejected the zlib stream (a bad Adler-32 or trailing junk; both are rejected identically in Node and Chromium).
- `PNG_BITDEPTH`: sub-8-bit gray in height mode (§4.3).
- `PNG_TOO_LARGE`: the allocation ceiling (§4.4).

`PNG_NO_INFLATE` is reserved for R8 (no `DecompressionStream`). `inspect` throws for structural faults and does not return partial info.

### 4.7 Implementation notes that should carry over
- The decoder streams IDAT parts straight into the `DecompressionStream` writer and writes the output into **one preallocated buffer** of the size IHDR implies. This replaces Step 5's `Blob` → `Response.arrayBuffer()` form, which costs a second full-size copy. Non-interlaced images are then **unfiltered in place**: row `y` is written at `y·rb` and read from `y·(rb+1)+1`, so writes never overtake reads. Together these save about 65 MiB at 16 MP RGBA.
- Extra inflated bytes beyond what IHDR implies produce the warning `PNG_EXTRA_IDAT_DATA:n` instead of failing; libpng behaves the same way.
- In tonal mode, an unequal-RGB or colour-palette PNG decodes to `policy: "raw-rgb"` with `channels: 3`. The plan's result type has no tonal colour shape. G2.14 sends tonal input to the browser decode anyway, so this branch exists only for completeness.

## 5. Decision

**Adopt the in-house raw decoder (`SBPng`) on `DecompressionStream`, as planned.** It is exact against libpng and deterministic across Node and Chromium. It fits comfortably inside the NFR-03 and NFR-04 budgets at the IMG-07 envelopes, and it needs no third-party code. No kill or fallback trigger was hit. R8 stays as written: feature-detect and block with an explanation, using `PNG_NO_INFLATE`.

## 6. Plan changes recommended (for the real S4 commit and G2.14)

1. **Error codes:** add `PNG_HEADER`, `PNG_INFLATE`, `PNG_BITDEPTH`, `PNG_TOO_LARGE` and `PNG_NO_INFLATE` to the S4 interface and to the G1.0 diagnostic registry.
2. **Allocation ceiling in `decode`** (`maxPixels`, default 2^26), independent of the IMG-07 preflight. Add the check `FUZZ REGRESSION: IHDR 2^31-1 x 2^31-1 → PNG_TOO_LARGE, no process abort`.
3. **Sub-8-bit gray (product owner decision):** the recommendation is to accept 1-, 2- and 4-bit gray in height mode through exact integer scaling (`raw-grayN-scaled8`, recorded as the policy) instead of rejecting it. ImageMagick writes such files by default. If the product owner prefers rejection, keep `PNG_BITDEPTH` with an explanatory message.
4. **Intake must call `inspect` with CRC verification in both modes** (state this in G2.14), because Chromium silently accepts APNG, 16-bit and ancillary-CRC corruption (§4.2). G4.8 should add a valid-APNG fixture and a 16-bit fixture to the browser suite.
5. **Step 5 wording:** use streamed writes into a preallocated buffer plus in-place unfilter instead of `Blob → Response.arrayBuffer()` (saves about 65 MiB peak at 16 MP RGBA). Also consider widening `sampleHash` to `hash(w, h, policy, samples)`, or document that it is only valid together with `w` and `h` (§4.5).

Also carry over: the 32 extended checks in `spikes/S4/run_tests.js` (Adam7 at all small sizes, sub-byte palettes, split IDAT, Adler and trailing-junk rejection, cross-encoding hash equality) should move into the `png.js` suite. `fuzz.js` is worth keeping as an occasional run rather than in `run_tests.js`, since 3,000 iterations take about 0.8 s.
